What is Bluetooth Low Energy?

Bluetooth Low Energy (BLE), introduced in Bluetooth 4.0, is a wireless communication protocol optimised for devices that must operate on tiny batteries for months or years. Unlike Classic Bluetooth, BLE uses short radio bursts rather than continuous streams, keeping current draw in the microamp range during idle periods.

ESP32 (all variants) includes a dual-mode Bluetooth radio. ESP-IDF exposes BLE through the Bluedroid stack (default) or, on newer chips, through the lighter NimBLE stack. This guide focuses on Bluedroid, which closely mirrors the Bluetooth SIG specification.

⚡

Low Energy

Designed for duty-cycled operation. A coin cell can last 1–5 years depending on connection interval.

📡

2.4 GHz ISM

Uses 40 × 2 MHz channels; 3 advertising channels and 37 data channels with frequency hopping.

📏

Range

Typically 10–100 m line-of-sight. BLE Long Range (Coded PHY) extends to 300–400 m.

🔗

Roles

Peripheral advertises and acts as server. Central scans, connects, and acts as client.

Core Concepts: GAP, GATT, Services & Characteristics

GAP — Generic Access Profile

GAP controls how devices advertise themselves, discover each other, and establish connections. A device in the Peripheral role broadcasts advertising packets every N milliseconds. A Central scans these packets, optionally filters by device name or UUID, and initiates a connection.

💡 Advertising Interval

Shorter intervals (e.g. 20 ms) make the device discoverable faster but consume more power. For IoT sensors, 500–1000 ms is a common balance. Minimum is 20 ms, maximum is 10.24 s.

GATT — Generic Attribute Profile

GATT defines how data is structured, read, written, and notified over a BLE connection. All application data exchange happens through GATT. GATT uses a client/server model:

  • GATT Server — holds a database of attributes (your ESP32 sensor node).
  • GATT Client — reads/writes attributes on the server (your phone app or another ESP32).

The GATT Hierarchy

Attribute hierarchy — top to bottom
Application
Your firmware — registers one or more Profiles
GATT Profile
Logical grouping (e.g. Heart Rate Profile). Contains services.
Service
Related functionality (e.g. Battery Service UUID 0x180F). Contains characteristics.
Characteristic
A single data point (e.g. Battery Level UUID 0x2A19). Contains a value + descriptors.
Descriptor
Metadata about a characteristic (e.g. CCCD 0x2902, User Description 0x2901).

UUIDs

Every service, characteristic, and descriptor is identified by a UUID (Universally Unique Identifier). Bluetooth SIG defines 16-bit UUIDs for standard services (e.g. 0x180F = Battery Service). Custom vendor services use full 128-bit UUIDs.

16-bit 0x180F 128-bit 12345678-1234-1234-1234-123456789ABC
ℹ️ 16-bit vs 128-bit UUIDs

16-bit UUIDs are shorthand — they are actually 128-bit with the Bluetooth Base UUID 0000XXXX-0000-1000-8000-00805F9B34FB. Use 16-bit for standard SIG-defined services, 128-bit for anything custom.

Handles

In the actual ATT (Attribute Protocol) layer, every attribute is referenced by a 16-bit handle — a sequential number assigned when services are registered. The handle is what the protocol actually uses over the air; UUIDs are looked up in the attribute table.

GATT Server — Architecture & Initialisation

A GATT Server on ESP32 consists of:

  • One or more Application Profiles — each has a unique app ID and its own callback.
  • Each profile registers Services, which contain Characteristics and Descriptors.
  • ESP-IDF uses an event-driven model — you register a global callback and a per-profile callback.

Initialisation sequence

c — main.c
#include "nvs_flash.h"
#include "esp_bt.h"
#include "esp_gap_ble_api.h"
#include "esp_gatts_api.h"
#include "esp_bt_main.h"
#include "esp_gatt_common_api.h"

void app_main(void)
{
    // 1. Init NVS (required for bonding key storage)
    esp_err_t ret = nvs_flash_init();
    if (ret == ESP_ERR_NVS_NO_FREE_PAGES ||
        ret == ESP_ERR_NVS_NEW_VERSION_FOUND) {
        ESP_ERROR_CHECK(nvs_flash_erase());
        ret = nvs_flash_init();
    }
    ESP_ERROR_CHECK(ret);

    // 2. Release Classic BT memory (BLE-only project)
    ESP_ERROR_CHECK(esp_bt_controller_mem_release(ESP_BT_MODE_CLASSIC_BT));

    // 3. Initialise and enable BT controller
    esp_bt_controller_config_t bt_cfg = BT_CONTROLLER_INIT_CONFIG_DEFAULT();
    ESP_ERROR_CHECK(esp_bt_controller_init(&bt_cfg));
    ESP_ERROR_CHECK(esp_bt_controller_enable(ESP_BT_MODE_BLE));

    // 4. Initialise and enable Bluedroid stack
    ESP_ERROR_CHECK(esp_bluedroid_init());
    ESP_ERROR_CHECK(esp_bluedroid_enable());

    // 5. Register GATTS and GAP callbacks
    ESP_ERROR_CHECK(esp_ble_gatts_register_callback(gatts_event_handler));
    ESP_ERROR_CHECK(esp_ble_gap_register_callback(gap_event_handler));

    // 6. Register application profile (app_id = 0)
    ESP_ERROR_CHECK(esp_ble_gatts_app_register(PROFILE_APP_ID));

    // 7. Set MTU (optional — default 23, max 517)
    esp_ble_gatt_set_local_mtu(500);
}
💡 MTU

MTU (Maximum Transmission Unit) is the largest payload per packet. Default is 23 bytes (20 bytes usable). Call esp_ble_gatt_set_local_mtu(500) early to allow the client to negotiate a larger MTU for faster bulk transfers.

Event handler skeleton

c
static void gatts_profile_event_handler(
    esp_gatts_cb_event_t event,
    esp_gatt_if_t gatts_if,
    esp_ble_gatts_cb_param_t *param)
{
    switch (event) {
    case ESP_GATTS_REG_EVT:
        /* Register succeeded — create service here */
        esp_ble_gatts_create_service(gatts_if, &gl_profile_tab[PROFILE_A_APP_ID].service_id, GATTS_NUM_HANDLE);
        /* Also start advertising */
        esp_ble_gap_set_device_name(SAMPLE_DEVICE_NAME);
        esp_ble_gap_config_adv_data(&adv_data);
        break;

    case ESP_GATTS_CREATE_EVT:
        gl_profile_tab[PROFILE_A_APP_ID].service_handle = param->create.service_handle;
        esp_ble_gatts_start_service(param->create.service_handle);
        esp_ble_gatts_add_char(
            param->create.service_handle,
            &gatts_demo_char1_uuid,
            ESP_GATT_PERM_READ | ESP_GATT_PERM_WRITE,
            ESP_GATT_CHAR_PROP_BIT_READ | ESP_GATT_CHAR_PROP_BIT_WRITE | ESP_GATT_CHAR_PROP_BIT_NOTIFY,
            &gatts_demo_char1_val, NULL);
        break;

    case ESP_GATTS_ADD_CHAR_EVT:
        gl_profile_tab[PROFILE_A_APP_ID].char_handle = param->add_char.attr_handle;
        /* Add CCCD descriptor to enable notifications */
        esp_ble_gatts_add_char_descr(
            gl_profile_tab[PROFILE_A_APP_ID].service_handle,
            ¬ify_descr_uuid,
            ESP_GATT_PERM_READ | ESP_GATT_PERM_WRITE, NULL, NULL);
        break;

    case ESP_GATTS_READ_EVT:
        handle_read_event(gatts_if, param);
        break;

    case ESP_GATTS_WRITE_EVT:
        handle_write_event(gatts_if, param);
        break;

    case ESP_GATTS_CONNECT_EVT:
        gl_profile_tab[PROFILE_A_APP_ID].conn_id = param->connect.conn_id;
        break;

    case ESP_GATTS_DISCONNECT_EVT:
        esp_ble_gap_start_advertising(&adv_params);
        break;

    default:
        break;
    }
}

Step-by-Step: Adding a Service

1 — Define your service UUID

c
/* 16-bit SIG-standard service UUID (Battery Service) */
#define GATTS_SERVICE_UUID_BATTERY   0x180F

/* OR — custom 128-bit UUID for your own service */
static uint8_t service_uuid128[16] = {
    /* LSB first (little-endian) */
    0xAB, 0xCD, 0xEF, 0x12, 0x34, 0x56,
    0x78, 0x9A, 0xBC, 0xDE, 0xF0, 0x12,
    0x34, 0x56, 0x78, 0x9A
};

2 — Define the service ID structure

c
static esp_gatt_srvc_id_t battery_service_id = {
    .id = {
        .uuid = {
            .len  = ESP_UUID_LEN_16,
            .uuid = { .uuid16 = GATTS_SERVICE_UUID_BATTERY },
        },
        .inst_id = 0,   /* instance ID (0 for first instance) */
    },
    .is_primary = true,   /* primary vs secondary service */
};

3 — Calculate and pass the number of handles

ℹ️ Handle Count Formula

Each attribute (service declaration, characteristic declaration, characteristic value, and each descriptor) needs one handle. Formula: 1 (service) + 2 × N_characteristics + N_descriptors. Example: 1 service + 2 characteristics + 2 CCCDs = 1 + 4 + 2 = 7 handles. Always add a safety buffer (e.g. +2).

c
#define GATTS_NUM_HANDLE_BATTERY  8   /* 1 svc + 2 chars + 2 CCCDs + 2 user descs + 1 buffer */

/* Called inside ESP_GATTS_REG_EVT: */
esp_ble_gatts_create_service(
    gatts_if,
    &battery_service_id,
    GATTS_NUM_HANDLE_BATTERY
);

4 — Start the service

c
/* Called inside ESP_GATTS_CREATE_EVT: */
uint16_t service_handle = param->create.service_handle;
esp_ble_gatts_start_service(service_handle);

Step-by-Step: Adding Characteristics

Define the characteristic UUID and initial value

c
#define GATTS_CHAR_UUID_BATTERY_LEVEL  0x2A19

static esp_gatt_char_prop_t a_property =
    ESP_GATT_CHAR_PROP_BIT_READ |
    ESP_GATT_CHAR_PROP_BIT_NOTIFY;

static uint8_t char1_str[] = { 0x64 };   /* initial value: 100 (%) */

static esp_attr_value_t gatts_char_val = {
    .attr_max_len = 1,
    .attr_len     = sizeof(char1_str),
    .attr_value   = char1_str,
};

static esp_bt_uuid_t char_uuid = {
    .len = ESP_UUID_LEN_16,
    .uuid = { .uuid16 = GATTS_CHAR_UUID_BATTERY_LEVEL },
};

Add the characteristic to the service

c
/* Called inside ESP_GATTS_CREATE_EVT (after esp_ble_gatts_start_service) */
esp_ble_gatts_add_char(
    service_handle,        /* from ESP_GATTS_CREATE_EVT */
    &char_uuid,            /* characteristic UUID */
    ESP_GATT_PERM_READ,    /* ATT permission: who can access */
    a_property,            /* GATT property: what operations */
    &gatts_char_val,       /* initial value (or NULL) */
    NULL                   /* auto-response control (NULL = manual) */
);
⚠️ Permission vs Property

Permission (ESP_GATT_PERM_*) controls the ATT-layer access (READ, WRITE, READ_ENCRYPTED, etc.). Property (ESP_GATT_CHAR_PROP_BIT_*) is what's advertised in the characteristic declaration to the GATT client. Set permissions at least as permissive as what you advertise in properties.

Permission constants quick reference

ConstantMeaning
ESP_GATT_PERM_READRead allowed (unencrypted)
ESP_GATT_PERM_READ_ENCRYPTEDRead allowed only when link is encrypted
ESP_GATT_PERM_READ_ENC_MITMRead allowed when encrypted + authenticated
ESP_GATT_PERM_WRITEWrite allowed (unencrypted)
ESP_GATT_PERM_WRITE_ENCRYPTEDWrite allowed only when link is encrypted
ESP_GATT_PERM_WRITE_ENC_MITMWrite allowed when encrypted + authenticated

Save the attribute handle

c
uint16_t char_handle;  /* store globally */

/* Inside ESP_GATTS_ADD_CHAR_EVT: */
case ESP_GATTS_ADD_CHAR_EVT:
    if (param->add_char.status == ESP_GATT_OK) {
        char_handle = param->add_char.attr_handle;
        ESP_LOGI(TAG, "Characteristic added, handle: 0x%04x", char_handle);
    }
    break;

Implementing Read, Write, Notify & Indicate

READ — Responding to a client read

When a client reads your characteristic, ESP_GATTS_READ_EVT fires. You must call esp_ble_gatts_send_response unless you set auto_rsp when adding the characteristic.

c
case ESP_GATTS_READ_EVT: {
    ESP_LOGI(TAG, "READ handle=%d, conn=%d, trans=%d",
        param->read.handle, param->read.conn_id, param->read.trans_id);

    esp_gatt_rsp_t rsp;
    memset(&rsp, 0, sizeof(esp_gatt_rsp_t));
    rsp.attr_value.handle = param->read.handle;

    /* Fill in your actual data */
    rsp.attr_value.len = 1;
    rsp.attr_value.value[0] = get_battery_level();  /* your function */

    esp_ble_gatts_send_response(
        gatts_if,
        param->read.conn_id,
        param->read.trans_id,
        ESP_GATT_OK,
        &rsp);
    break;
}
💡 Auto-response

Pass an esp_attr_control_t with auto_rsp = ESP_GATT_AUTO_RSP to esp_ble_gatts_add_char to let the BLE stack reply automatically with the stored attribute value. Use manual response (ESP_GATT_RSP_BY_APP) when you need to return live/computed data.

WRITE — Handling a client write

c
case ESP_GATTS_WRITE_EVT: {
    ESP_LOGI(TAG, "WRITE handle=%d len=%d, is_prep=%d need_rsp=%d",
        param->write.handle, param->write.len,
        param->write.is_prep, param->write.need_rsp);

    if (!param->write.is_prep) {
        /* Normal write — process immediately */
        handle_write_data(param->write.value, param->write.len);

        if (param->write.need_rsp) {
            esp_ble_gatts_send_response(
                gatts_if,
                param->write.conn_id,
                param->write.trans_id,
                ESP_GATT_OK, NULL);
        }
    } else {
        /* Prepared write (long write) — buffer it */
        prepare_write_env_cb(&prepare_write_env, gatts_if, param);
    }
    break;
}

NOTIFY — Server pushes data to client

Notifications are sent from your code whenever data changes. The client does not ACK them. Notifications only reach the client if they have enabled notifications via the CCCD descriptor.

c
uint8_t notify_data[4] = { 0x01, 0x02, 0x03, 0x04 };

esp_ble_gatts_send_indicate(
    gatts_if,
    conn_id,             /* saved from ESP_GATTS_CONNECT_EVT */
    char_handle,         /* attribute handle */
    sizeof(notify_data),
    notify_data,
    false               /* false = NOTIFY (no ACK), true = INDICATE (ACK required) */
);

INDICATE — Same API, with acknowledgement

c
esp_ble_gatts_send_indicate(
    gatts_if, conn_id, char_handle,
    sizeof(notify_data), notify_data,
    true   /* ← true = INDICATION. Wait for ESP_GATTS_CONF_EVT before sending next */
);

/* ESP_GATTS_CONF_EVT fires when client sends the ACK */
case ESP_GATTS_CONF_EVT:
    if (param->conf.status != ESP_GATT_OK) {
        ESP_LOGE(TAG, "Indication failed, status=%d", param->conf.status);
    }
    break;
⚠️ Do not queue indications

You must wait for ESP_GATTS_CONF_EVT before sending another indication. Sending a second indication before the first is confirmed will result in an error. Use a flag or semaphore.

User Description Descriptor (0x2901)

The Characteristic User Description descriptor (UUID 0x2901) lets you attach a human-readable UTF-8 string to any characteristic. Phone apps and BLE debuggers will display this string next to the characteristic.

c
static esp_bt_uuid_t user_descr_uuid = {
    .len = ESP_UUID_LEN_16,
    .uuid = { .uuid16 = ESP_GATT_UUID_CHAR_DESCRIPTION },  /* 0x2901 */
};

static uint8_t user_desc[] = "Battery Level (%)";

static esp_attr_value_t user_descr_val = {
    .attr_max_len = sizeof(user_desc),
    .attr_len     = sizeof(user_desc) - 1,   /* exclude null terminator */
    .attr_value   = user_desc,
};

/* Add inside ESP_GATTS_ADD_CHAR_EVT after saving char_handle: */
esp_ble_gatts_add_char_descr(
    service_handle,
    &user_descr_uuid,
    ESP_GATT_PERM_READ,   /* read-only */
    &user_descr_val,
    NULL
);
12

CCCD — Client Characteristic Configuration Descriptor (0x2902)

The CCCD is a 2-byte descriptor that the client writes to enable notifications or indications. Without a CCCD, the client cannot turn on notifications even if the characteristic has the NOTIFY property.

  • Client writes 0x0001 to enable Notifications.
  • Client writes 0x0002 to enable Indications.
  • Client writes 0x0000 to disable both.

Adding the CCCD

c
static esp_bt_uuid_t notify_descr_uuid = {
    .len = ESP_UUID_LEN_16,
    .uuid = { .uuid16 = ESP_GATT_UUID_CHAR_CLIENT_CONFIG },  /* 0x2902 */
};

static uint8_t  notify_ccc[2]     = { 0x00, 0x00 };  /* initially disabled */
static esp_attr_value_t notify_ccc_val = {
    .attr_max_len = 2,
    .attr_len     = 2,
    .attr_value   = notify_ccc,
};

/* Add after the characteristic: */
esp_ble_gatts_add_char_descr(
    service_handle,
    ¬ify_descr_uuid,
    ESP_GATT_PERM_READ | ESP_GATT_PERM_WRITE,
    ¬ify_ccc_val, NULL
);

Detecting when the client enables notifications

c
static bool notify_enabled = false;

case ESP_GATTS_WRITE_EVT:
    if (param->write.handle == cccd_handle && param->write.len == 2) {
        uint16_t descr_value = (param->write.value[1] << 8) | param->write.value[0];
        if (descr_value == 0x0001) {
            notify_enabled = true;
            ESP_LOGI(TAG, "Notifications ENABLED");
        } else if (descr_value == 0x0002) {
            notify_enabled = true;
            ESP_LOGI(TAG, "Indications ENABLED");
        } else if (descr_value == 0x0000) {
            notify_enabled = false;
            ESP_LOGI(TAG, "Notify/Indicate DISABLED");
        }
    }
    break;

Complete GATT Server — Putting It All Together

Below is a condensed but complete GATT server example: one service with a readable/writable/notifiable characteristic, a CCCD, and a user description. The advertising packet includes the service UUID so clients can filter by it.

c — gatts_demo.c (condensed)
#include <string.h>
#include "esp_log.h"
#include "esp_bt.h"
#include "esp_gap_ble_api.h"
#include "esp_gatts_api.h"
#include "esp_bt_main.h"

#define TAG              "GATTS_DEMO"
#define DEVICE_NAME      "ESP32_BLE"
#define SVC_UUID         0xFF00
#define CHAR_UUID        0xFF01
#define NUM_HANDLES      8
#define APP_ID           0

static uint16_t svc_handle, char_handle, cccd_handle, conn_id_g = 0xFFFF;
static esp_gatt_if_t gatts_if_g;
static bool notify_en = false;

/* Advertising data — include SVC UUID for filtering */
static uint8_t adv_service_uuid128[4] = {
    0x00, 0xFF, 0x00, 0xFF
};
static esp_ble_adv_data_t adv_data = {
    .set_scan_rsp        = false,
    .include_name        = true,
    .include_txpower     = false,
    .min_interval        = 0x0006,
    .max_interval        = 0x0010,
    .appearance          = 0,
    .manufacturer_len    = 0,
    .p_manufacturer_data = NULL,
    .service_data_len    = 0,
    .p_service_data      = NULL,

    .p_service_uuid      = adv_service_uuid128,
    .flag = (ESP_BLE_ADV_FLAG_GEN_DISC | ESP_BLE_ADV_FLAG_BREDR_NOT_SPT),
};
static esp_ble_adv_params_t adv_params = {
    .adv_int_min        = 0x20,
    .adv_int_max        = 0x40,
    .adv_type           = ADV_TYPE_IND,
    .own_addr_type      = BLE_ADDR_TYPE_PUBLIC,
    .channel_map        = ADV_CHNL_ALL,
    .adv_filter_policy  = ADV_FILTER_ALLOW_SCAN_ANY_CON_ANY,

static void gap_event_handler(esp_gap_ble_cb_event_t event,
                               esp_ble_gap_cb_param_t *param)
{
    if (event == ESP_GAP_BLE_ADV_DATA_SET_COMPLETE_EVT)
        esp_ble_gap_start_advertising(&adv_params);
}

static void gatts_event_handler(esp_gatts_cb_event_t event,
                                  esp_gatt_if_t gatts_if,
                                  esp_ble_gatts_cb_param_t *param)
{
    switch(event) {
    case ESP_GATTS_REG_EVT: {
        gatts_if_g = gatts_if;
        esp_ble_gap_set_device_name(DEVICE_NAME);
        esp_ble_gap_config_adv_data(&adv_data);
        esp_gatt_srvc_id_t svc_id = {
            .id = { .uuid = { .len = ESP_UUID_LEN_16,
                              .uuid = { .uuid16 = SVC_UUID } }, .inst_id = 0 },
            .is_primary = true
        };
        esp_ble_gatts_create_service(gatts_if, &svc_id, NUM_HANDLES);
        break;
    }
    case ESP_GATTS_CREATE_EVT: {
        svc_handle = param->create.service_handle;
        esp_ble_gatts_start_service(svc_handle);
        esp_bt_uuid_t char_uuid = { .len = ESP_UUID_LEN_16,
                                    .uuid = { .uuid16 = CHAR_UUID } };
        uint8_t val[] = { 0x00 };
        esp_attr_value_t char_val = { .attr_max_len=20, .attr_len=1, .attr_value=val };
        esp_ble_gatts_add_char(svc_handle, &char_uuid,
            ESP_GATT_PERM_READ | ESP_GATT_PERM_WRITE,
            ESP_GATT_CHAR_PROP_BIT_READ | ESP_GATT_CHAR_PROP_BIT_WRITE |
            ESP_GATT_CHAR_PROP_BIT_NOTIFY,
            &char_val, NULL);
        break;
    }
    case ESP_GATTS_ADD_CHAR_EVT: {
        char_handle = param->add_char.attr_handle;
        esp_bt_uuid_t cccd_uuid = { .len = ESP_UUID_LEN_16,
            .uuid = { .uuid16 = ESP_GATT_UUID_CHAR_CLIENT_CONFIG } };
        uint8_t ccc[] = { 0x00, 0x00 };
        esp_attr_value_t ccc_val = { .attr_max_len=2, .attr_len=2, .attr_value=ccc };
        esp_ble_gatts_add_char_descr(svc_handle, &cccd_uuid,
            ESP_GATT_PERM_READ | ESP_GATT_PERM_WRITE, &ccc_val, NULL);
        break;
    }
    case ESP_GATTS_ADD_CHAR_DESCR_EVT:
        cccd_handle = param->add_char_descr.attr_handle;
        break;
    case ESP_GATTS_CONNECT_EVT:
        conn_id_g = param->connect.conn_id;
        break;
    case ESP_GATTS_DISCONNECT_EVT:
        conn_id_g = 0xFFFF;
        notify_en = false;
        esp_ble_gap_start_advertising(&adv_params);
        break;
    case ESP_GATTS_READ_EVT: {
        esp_gatt_rsp_t rsp; memset(&rsp, 0, sizeof(rsp));
        rsp.attr_value.handle = param->read.handle;
        rsp.attr_value.len    = 1;
        rsp.attr_value.value[0] = 42;  /* replace with real data */
        esp_ble_gatts_send_response(gatts_if, param->read.conn_id,
            param->read.trans_id, ESP_GATT_OK, &rsp);
        break;
    }
    case ESP_GATTS_WRITE_EVT:
        if (param->write.handle == cccd_handle && param->write.len == 2) {
            notify_en = (param->write.value[0] == 0x01);
        }
        if (param->write.need_rsp)
            esp_ble_gatts_send_response(gatts_if, param->write.conn_id,
                param->write.trans_id, ESP_GATT_OK, NULL);
        break;
    default: break;
    }
}

/* Call this from a timer/task to push updates */
void ble_send_notify(uint8_t *data, uint16_t len) {
    if (notify_en && conn_id_g != 0xFFFF)
        esp_ble_gatts_send_indicate(gatts_if_g, conn_id_g,
            char_handle, len, data, false);
}

GATT Client — Overview

A GATT Client (Central role) scans for advertising packets, connects to a peripheral, discovers its services and characteristics, then reads/writes/subscribes to them. On ESP32 you use the esp_ble_gattc_* API.

ℹ️ Typical client workflow

Scan → Filter → Connect → Discover services → Find characteristic handle → Read/Write/Register notify. Each step is triggered by an event from the previous step — it's a state machine.

        esp_ble_gattc_get_descr_by_char_handle(gattc_if,
            gl_profile_tab[PROFILE_A_APP_ID].conn_id,
            char_hdl, cccd_uuid, &descr_elem, &dcnt);
        if (dcnt > 0) cccd_hdl = descr_elem.handle;
    }
    break;
}

Pairing, Bonding & BLE Security

BLE security operates in distinct phases. Understanding the terminology is essential before writing security code:

🤝
Pairing
The one-time process of exchanging keys to establish an encrypted, optionally authenticated, link. Pairing generates Long-Term Keys (LTK), Identity Resolving Keys (IRK), and Connection Signature Resolving Keys (CSRK).
🔗
Bonding
Storing the pairing keys in non-volatile memory (NVS on ESP32) so the devices can re-connect and re-encrypt without pairing again. A bonded device is a "known device."
🔑
Encryption
Once pairing is done, the link is encrypted using the LTK. Subsequent connections use the stored LTK directly (no re-pairing needed).
✅
Authentication (MITM protection)
Proving the peer is who it claims to be, not a man-in-the-middle. Achieved via passkey entry, numeric comparison, or OOB. Without MITM protection, encryption is present but unauthenticated.
🆕
LE Secure Connections (LESC)
BLE 4.2+ Elliptic Curve Diffie-Hellman key exchange. Significantly stronger than legacy pairing. Enabled with ESP_BLE_SM_ONLY_ACCEPT_SPECIFIED_SEC_AUTH.
21

IO Capabilities — Choosing the Right Mode

The pairing method depends on what input/output the device physically has. Both sides declare their IO capabilities and the Bluetooth spec determines which pairing method is used:

ConstantValueDevice has…Pairing method
ESP_IO_CAP_NONE3No display, no keyboardJust Works (no MITM protection)
ESP_IO_CAP_OUT1Display only (no keyboard)Passkey Display — server shows 6-digit code, user enters on other device
ESP_IO_CAP_IN2Keyboard only (no display)Passkey Entry — user types passkey shown on the other device
ESP_IO_CAP_IO4Keyboard + displayNumeric Comparison (BLE SC) or Passkey Entry (Legacy)
ESP_IO_CAP_KBDISP0Keyboard + display (combined)Best available — Numeric Comparison preferred

Pairing method matrix

The Bluetooth spec combines the two sides' IO caps to select the association model:

Initiator ↓ / Responder →NoInput/NoOutputDisplay OnlyDisplay+KeyboardKeyboard Only

💡 IoT Devices Recommendation

For a headless sensor (no display, no keyboard) use ESP_IO_CAP_NONE. This results in "Just Works" pairing — no user interaction, but also no MITM protection. For higher security, use ESP_IO_CAP_OUT with a display (show passkey) or ESP_IO_CAP_IN with a button (fixed passkey entry).

Security Modes & Levels

BLE defines Security Modes and within them Levels of protection that a characteristic can require:

ModeLevelRequirement
Mode 1Level 1No security (no encryption, no authentication)
Mode 1Level 2Unauthenticated pairing with encryption (Just Works)
Mode 1Level 3Authenticated pairing with encryption (MITM protected)
Mode 1Level 4Authenticated LE SC pairing with encryption (strongest)
Mode 2Level 1Unauthenticated pairing with data signing
Mode 2Level 2Authenticated pairing with data signing

In ESP-IDF, you enforce a security mode by using ESP_GATT_PERM_READ_ENCRYPTED / ESP_GATT_PERM_WRITE_ENCRYPTED (Level 2) or ESP_GATT_PERM_READ_ENC_MITM / ESP_GATT_PERM_WRITE_ENC_MITM (Level 3) on characteristics.

Implementing Pairing & Bonding in Code

1 — Configure security parameters

c
void setup_ble_security(void)
{
    /* Authentication requirements */
    esp_ble_auth_req_t auth_req = ESP_LE_AUTH_REQ_SC_MITM_BOND;
    /*
     * ESP_LE_AUTH_NO_BOND          — no bonding, no MITM
     * ESP_LE_AUTH_BOND             — bond, no MITM (Just Works)
     * ESP_LE_AUTH_REQ_MITM         — no bond, MITM (passkey)
     * ESP_LE_AUTH_REQ_SC_ONLY      — LE SC, no bond
     * ESP_LE_AUTH_REQ_SC_BOND      — LE SC + bond
     * ESP_LE_AUTH_REQ_SC_MITM      — LE SC + MITM, no bond
     * ESP_LE_AUTH_REQ_SC_MITM_BOND — LE SC + MITM + bond (strongest)
     */
    esp_ble_gap_set_security_param(ESP_BLE_SM_AUTHEN_REQ_MODE,
        &auth_req, sizeof(uint8_t));

    /* IO capability of this device */
    esp_ble_io_cap_t iocap = ESP_IO_CAP_NONE;   /* headless device */
    esp_ble_gap_set_security_param(ESP_BLE_SM_IOCAP_MODE,
        &iocap, sizeof(uint8_t));

    /* Key distribution — what keys each side sends */
    uint8_t init_key = ESP_BLE_ENC_KEY_MASK | ESP_BLE_ID_KEY_MASK;
    uint8_t rsp_key  = ESP_BLE_ENC_KEY_MASK | ESP_BLE_ID_KEY_MASK;
    esp_ble_gap_set_security_param(ESP_BLE_SM_SET_INIT_KEY,
        &init_key, sizeof(uint8_t));
    esp_ble_gap_set_security_param(ESP_BLE_SM_SET_RSP_KEY,
        &rsp_key, sizeof(uint8_t));

    /* Maximum bonded devices to store */
    uint8_t max_bonds = 4;
    esp_ble_gap_set_security_param(ESP_BLE_SM_MAX_BOND_DEV_NUM,
        &max_bonds, sizeof(uint8_t));

    /* Only accept specified security auth */
    uint8_t only_accept = ESP_BLE_ONLY_ACCEPT_SPECIFIED_AUTH_ENABLE;
    esp_ble_gap_set_security_param(ESP_BLE_SM_ONLY_ACCEPT_SPECIFIED_SEC_AUTH,
        &only_accept, sizeof(uint8_t));
}

⚠️ NVS must not be erased

Bond keys are stored in NVS. Calling nvs_flash_erase() removes all bond data — only do this intentionally during development or factory reset flows.

Reconnecting to a bonded device

When a bonded central reconnects, the stack automatically uses the stored LTK to encrypt the link without user interaction. The server should call esp_ble_set_encryption again after ESP_GATTS_CONNECT_EVT to ensure the link re-encrypts using the stored bond.

Glossary

TermDefinition
ATTAttribute Protocol — low-level protocol for reading/writing attributes over a BLE connection.
AttributeAny piece of data in the GATT database: service declaration, characteristic declaration, value, or descriptor.
BDABluetooth Device Address — 6-byte MAC-like address. Can be public, static random, resolvable private, or non-resolvable private.
BLE SC / LESCLE Secure Connections — BLE 4.2+ ECDH-based key exchange. Replaces legacy SMP for higher security.
CCCDClient Characteristic Configuration Descriptor (UUID 0x2902) — written by the client to enable notify (0x0001) or indicate (0x0002).
CentralGAP role that scans and initiates connections. Also the GATT Client role in practice.
CharacteristicA typed data value in a GATT service, with properties (read/write/notify) and an optional set of descriptors.
conn_idConnection identifier — a number assigned by the stack to each active connection. Required for most GATTS/GATTC API calls.
CSRKConnection Signature Resolving Key — used for data signing (Security Mode 2).
GAPGeneric Access Profile — governs device discovery, advertising, and connection procedures.
gatts_ifGATTS interface identifier — like a file descriptor for the GATT server instance. Passed to most GATTS API calls.
GATTGeneric Attribute Profile — defines how data is organised and transferred over BLE.
Handle16-bit number referencing an attribute in the ATT database. Assigned sequentially when services are registered.
IndicationServer-initiated data push that requires a confirmation (ACK) from the client. More reliable than Notification.
IRKIdentity Resolving Key — allows resolution of a peer's randomised private address back to its real identity.
Just WorksPairing method with no user interaction. Encrypts the link but provides no MITM protection.
LTKLong-Term Key — the main encryption key. Stored during bonding for re-encryption on subsequent connections.
MITMMan-in-the-Middle. BLE security level 3+ is MITM-protected, meaning a passive eavesdropper cannot inject data.
MTUMaximum Transmission Unit — max payload per ATT packet. Default 23 bytes; can be negotiated up to 517 bytes.
NotificationServer-initiated data push with no ACK from client. Fast and low-overhead but delivery not guaranteed.
NVSNon-Volatile Storage — ESP-IDF key-value store in flash. Used by Bluedroid to persist bonding keys.
OOBOut-of-Band — pairing using a channel other than BLE (e.g. NFC, QR code) to exchange keys.
Passkey6-digit number used to confirm pairing identity. One device displays it, the other inputs it.
PeripheralGAP role that advertises and accepts connections. Also the GATT Server role in practice.
ProfileA collection of services designed to fulfil a specific use case (e.g. Heart Rate Profile).
ServiceA logical container for related characteristics, identified by a UUID.
SMPSecurity Manager Protocol — the pairing and key exchange protocol in BLE.
UUIDUniversally Unique Identifier — 16-bit (SIG-defined) or 128-bit (custom) identifier for services, characteristics, and descriptors.
